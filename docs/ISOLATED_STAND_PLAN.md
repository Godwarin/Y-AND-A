# Изолированный стенд BETA-0.42

Владелец разрешил установку VirtualBox и принял условия гостевой Windows. Установлен VirtualBox 7.2.22, компонент VBoxApplication. Подпись Oracle и SHA-256 установщика проверены. Контрольная сумма ISO Windows 11 Enterprise Evaluation совпала с опубликованной Microsoft. Подтверждения сохранены в `docs/evidence/virtualbox-setup.json` и `docs/evidence/windows-guest-iso.json`.

У VM два виртуальных процессора, 4 ГиБ памяти, системный диск 64 ГиБ и отдельный рабочий диск 512 МиБ. Все восемь сетевых адаптеров отключены. В гостевой NTFS предусмотрена жёсткая квота 128 МиБ для тестовой учётной записи. Перед запуском приложения пробный процесс должен получить отказ при расширении файла сверх квоты. Фактические результаты указываются в TEST_RESULTS.md.

До аудита разрешена лишь подготовка чистой guest baseline. Не подключать к guest настоящие ключи, backup, пользовательский HOME, рабочий project root, аккаунты и телефоны. Никаких shared folders/clipboard/drag-and-drop/USB/bridged networking/Guest Additions для интеграции с host. Перед target execution отключить все NIC VM; клиенты/серверы только в её loopback. Тестовые инструменты брать из уже доступных локально зависимостей, переносить только явно отобранные публичные файлы через read-only образ; не запускать установку зависимостей/скачивание из target scripts.

## Обязательные условия до первого target process

1. ОС guest действительно изолирована от внешней сети и host/shared services; оба loopback endpoint находятся только внутри guest.
2. Target запускается отдельным непривилегированным restricted principal. Target/toolchain доступны ему только для чтения; запись возможна только в назначенный scratch. Обычного отдельного пользователя без проверки всех writable paths недостаточно.
3. Запуск из пустого environment с явным allowlist безопасных значений; HOME/TEMP/APPDATA/cache находятся в scratch. Реальные Windows credentials и унаследованное окружение не передаются.
4. OS-enforced Job/container controls для CPU/RAM/process count/wall time и файловых/дисковых квот, включая всех детей. Целевые начальные пределы:2GiB на job,16 процессов,20%CPU,180s на case, scratch512MiB. Конкретные API/пределы должны быть реализованы и проверены на безопасном dummy до тестов.
5. Проверить запрет записи вне scratch, отсутствие внешней сети, ограничение ресурсов и завершение всех детей. Если хотя бы один контроль недоказан — не выполнять target tests и оставить NEEDS_VALIDATION.

Сам факт установки VirtualBox или запуска VM не означает соответствие security-audit. На этом этапе никакой PASS не заявляется.

## Порядок тестирования и отчёт

Привязать результаты к точным application hashes BETA-0.42 (внутренняя версия0.4.0-rc.1). Сначала минимальные13 негативных regressions: Android deadlines/slow peer recovery/token/pin/one-use; AirPlay unauth routes/body limits/spoof/approval DENY/ALLOW/expiry/replay/key mismatch/client cap. Затем protocol/native pixel/lifecycle cases, не затрагивая живой телефон. Записывать команды, synthetic fixture inputs, allowlist environment и фактические лимиты.

Не переносить произвольные guest files на host. Для focused validation использовать только минимальный проверенный результат; для полного six-phase audit требуется предусмотренный навыком race-safe parent-side artifact promotion и независимая верификация. Пока стенд и проверки не завершены, чистый GitHub snapshot можно подготовить локально; загрузку по установленному владельцем порядку выполнять после security этапа. Репозиторий оставить private.

## Проверка совместимости системной криптографии

Нативный пробный процесс проверяет запись в scratch, отказ записи в исходники, инструменты и системные каталоги, жёсткую квоту, безопасное окружение родителя и потомка. Контроллер подтверждает создание и завершение дочернего процесса. Отдельный клиент и сервер обмениваются байтом через TCP на 127.0.0.1.

При загрузке системной bcrypt.dll под ограниченной учётной записью получен Win32 1114. Проверка открывает гостевые устройства CNG и KsecDD, запрашивает разные маски доступа и сразу закрывает полученные дескрипторы. Пробный процесс не делает запросов IOCTL и не использует ключи. Системные объекты допускают чтение, а открытие на запись в проверенной конфигурации завершается отказом. Это две наблюдаемые величины. Какое конкретно обращение из библиотеки вызвало её отказ, ещё предстоит установить.

Для сравнения контроллер может запустить собственный пробник, который загружает только системную bcrypt.dll и сразу завершается. Другие параметры тестового токена применимы только к этому пробнику. Приёмники, Python и тестовые сценарии под сравнительным токеном не запускаются. Вывод пробника — числовой код. Успех сравнения не меняет решение о готовности выпуска.

### Следующий эксперимент при отдельном согласии владельца

1. Сохранить контрольную точку только тестовой VM. Зафиксировать исходный дескриптор доступа выбранного гостевого криптоустройства и проверить право вернуть его через тот же открытый дескриптор. При отказе остановиться.
2. Только в этом снимке временно разрешить ограничивающему SID пустой тестовой группы тот доступ к одному криптоустройству, который уже получает обычный пользователь. Сначала проверить KsecDD отдельно. Участников в группе быть не должно. Не добавлять Everyone в токен приложения и не выдавать права смены владельца или прав доступа. Уточнить минимальную маску на служебном пробнике. При необходимости проверить CNG отдельным опытом с откатом первого изменения.
3. Сопоставить результат загрузки bcrypt.dll с исходным результатом 1114. Любая проверка продукта по-прежнему требует независимого подтверждения изоляции, рабочего окна и очистки дочерних процессов в той же конфигурации. Эксперимент с DLL сам по себе проверкой Y AND A не является.
4. Восстановить исходный дескриптор через сохранённый дескриптор объекта, перечитать его и сравнить с исходным. При ошибке откатить снимок. Рабочая Windows пользователя в эксперименте не участвует.

Граница согласования — временное изменение системных правил доступа внутри гостевой ОС. Исходное разрешение на VirtualBox и установку Windows, а также правила проекта о работе в собственных каталогах такой случай отдельно не описывают.
