# GitHub с нуля на примере Y AND A

GitHub — место для хранения проекта, его истории и готовых выпусков. Трансляция экрана через GitHub не проходит: Y AND A по-прежнему соединяет телефон и ПК в локальной сети.

## Два места для разных задач

**Code** — исходники программы: React-интерфейс, Android-приложение, native receivers, инструкции и лицензии. Разработчик может прочитать их, предложить исправление или собрать свою версию. Обычному пользователю запускать исходники не требуется.

**Releases** — готовые версии для скачивания. В выпуске BETA-0.42 будут Windows ZIP, Android APK, полный архив исходников с закреплёнными зависимостями и файлы проверки. [GitHub описывает Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) как версии программы с описанием и прикреплёнными загрузками.

**Code → Download ZIP** скачивает копию исходников из репозитория. Это не Windows-программа. Автоматические ссылки **Source code (zip/tar.gz)** в Releases тоже создаёт GitHub; наш отдельный `Y-AND-A-BETA-0.42-source.zip` дополнительно содержит закреплённые исходные пакеты зависимостей.

## Пять слов, которые встретятся

| Термин | Что это означает здесь |
|---|---|
| Repository / репозиторий | Папка проекта на GitHub: Godwarin/Y-AND-A |
| Commit / коммит | Сохранённая порция изменений с описанием; история помогает понять, что поменялось |
| Branch / ветка | Линия разработки; основная ветка называется main |
| Tag / метка | Указатель на точный коммит; BETA-0.42 свяжет код с первым бета-выпуском |
| Release / выпуск | Страница версии с описанием и файлами для пользователей |

## Что подготовлено локально

- `publish/github` — только проверенные файлы, которые пойдут в Code. Ключей, SDK, кэшей и виртуальной машины там нет.
- `release/BETA-0.42` — готовые файлы для Releases. Windows ZIP содержит EXE, библиотеки и инструкции; APK устанавливается на Android.
- `docs/RELEASE_NOTES_BETA_0.42.md` — описание выпуска. `LICENSE`, `THIRD_PARTY_NOTICES.md`, `SECURITY.md` и русские шаблоны Issues поясняют права, ограничения и обратную связь.
- `publish/upload-plan.json` — локальная ведомость будущей выгрузки: целевой репозиторий, hashes, список загрузок и параметры беты. Этот служебный файл не загружается в Code.

Закрытые ключи подписывают новые версии и остаются только у автора. Открытый ключ, сертификат APK и контрольные суммы помогают проверять файлы и могут распространяться. Подпись манифеста проверяют с заранее доверенным отпечатком издателя; ключ из той же загрузки сам по себе не решает вопрос доверия к первой загрузке.

## Как пройдёт первая выгрузка

1. Повторно проверяем, что репозиторий принадлежит Godwarin, остаётся закрытым и в нём не появились чужие изменения.
2. Загружаем чистую копию исходников в main одним начальным коммитом. Ни исходная рабочая папка целиком, ни её скрытые каталоги не отправляются.
3. Создаём метку BETA-0.42 на этом коммите и черновик Release с признаком Pre-release. Прикрепляем семь подготовленных файлов.
4. Сверяем hashes загруженных файлов. Проверяем описание и установочную инструкцию. Пока выпуск — Draft, пользователи с обычным доступом на чтение его не видят.
5. Автор решает, кому открыть проект и когда публиковать выпуск. Private означает доступ приглашённым участникам; Public — открытое чтение кода и опубликованных загрузок.

На момент подготовки, 5 ноября 2026 года, репозиторий закрыт и пуст. Эта инструкция описывает следующий этап; загрузка и открытие доступа ещё не выполнены. [Доступ к опубликованным Releases связан с доступом на чтение репозитория](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

После явного решения открыть Public, сразу после смены видимости и до анонса выпуска нужно включить **Settings → Advanced Security → Private vulnerability reporting**. Тогда человек сможет сообщить об уязвимости через **Security → Advisories → Report a vulnerability**, без публичного раскрытия деталей. [Официальная инструкция GitHub](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository) описывает эту настройку для публичных репозиториев. Сейчас настройка удалённо не менялась.

## Что будет после первого выпуска

Пользователь скачает Windows ZIP/APK в Releases и откроет Issue, если найдёт ошибку. Исправления появятся в новых коммитах. Для новой готовой версии создаётся новая метка и новый Release с новыми проверенными файлами. Старую версию сохраняют отдельно; файл на GitHub не обновляет уже установленную программу автоматически.

Другие разработчики могут сделать **Fork** — свою копию проекта — и прислать **Pull request**, то есть предложение изменений. Это не меняет ваш код автоматически: предложение сначала просматривает и принимает владелец. GPL-3.0-only разрешает работу с кодом при соблюдении лицензии; закрытые ключи для этого не выдаются.
